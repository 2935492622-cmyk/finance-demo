## 文件修改边界

| 角色 | 可修改范围 | 默认只读 / 不得修改 |

| 主 Agent | 根文档、`.codex/`、`docs/` 规划、`database/`、集成配置与必要协调修复 | 不覆盖子 Agent 正在负责的文件；先协调所有权 |

`docs/TEST_PLAN.md` 为主 Agent 的验收基线；QA 可在 `docs/qa/` 中补充详细用例、缺陷报告、执行报告及截图说明，不擅自降低基线。模块交付报告分别为 `frontend/DELIVERY.md`、`backend/DELIVERY.md`、`docs/qa/DELIVERY.md`。主 Agent 汇总到最终报告与 README。

backend-developer 落实模型与连接，若数据库设计需修改先报告主 Agent，由主 Agent维护 schema.sql；前端依赖由前端 Agent 安装，后端依赖由后端 Agent 安装，QA 需要新测试依赖时先由主 Agent 协调，不能同时改同一份锁文件。

## 交付报告模板

每个角色必须报告以下内容，命令未执行时明确注明：

1. 完成内容及对应任务编号。
2. 新增 / 修改文件列表。
3. 实现方案、核心数据流和应理解的知识点。
4. 启动方式、环境前提和配置要求。
5. 实际测试命令。
6. 测试结果与证据（通过 / 失败 / 未执行 / 受阻）。
7. 未解决问题、限制及所依赖的其他模块。

## 缺陷与契约变更流程

QA 给出缺陷编号、复现步骤、期望 / 实际结果和脱敏证据 → 主 Agent 判断模块与严重程度 → 对应开发 Agent 修复并解释根因 → QA 执行复测 → 主 Agent 确认关闭。QA 不仅阅读代码就判定通过，也不直接大范围修改业务代码。

接口冲突必须暂停依赖该冲突的工作，向主 Agent 报告；不允许前后端各自改字段“先跑起来”。已确认契约调整需用户确认并同步 API、DB 设计、SQL、模型和测试用例。

## 学习过程展示

每个阶段开始说明目标和依赖；每个模块交付解释组件、校验、事务或汇总的核心逻辑；遇到 Bug 说明触发条件及根因；阶段结束报告实测结果和下一步。用户确认第二阶段前，不派发业务开发任务。
